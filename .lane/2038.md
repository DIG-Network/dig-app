# Lane: #2038 — branded prompt GUI

Tracking: https://github.com/DIG-Network/dig_ecosystem/issues/2038

## Phase 1 — stack decision: **Rust-native (egui), not a webview**

Both candidates were built as real, working `SignPrompt` windows in dig-installer's visual language
and measured on the same machine (Windows 11, release builds, 5 runs each).

| | current (Win32 GDI) | **A — webview** (wry 0.46 + tao 0.30 / WebView2) | **B — Rust-native** (egui 0.31 / eframe-glow) |
|---|---|---|---|
| time to first paint, from the "show a prompt" call | ~60 ms | **411 ms** avg (366–481; a second batch 360–711) | **~90 ms** median (80/83/86/92/97/113; one 549 ms cold-GPU first run) |
| working set, whole process TREE | 14 MB | **390 MB** | 114 MB |
| private bytes, whole process tree | 2 MB | **190 MB** | **55 MB** |
| processes per prompt | 1 | **7** (host + 6 `msedgewebview2.exe`) | **1** |
| binary | — | 0.8 MB + the WebView2 runtime | 3.5 MB, self-contained |
| polish vs the dig-installer bar | far below | reached immediately | reached, after real work |
| markup injection in the spend-authorising window | n/a | **per-call-site, forever** | **impossible by construction** |

### The escaping result is the one that decides it

The webview prototype takes a `PROTO_NO_ESCAPE=1` switch that removes **one** `esc()` call at **one**
render site. With it, an attacker-supplied decoded-transaction string renders as a complete forged
consent UI *inside the real consent window*: a green `✓ Verified by DIG — low-value test transfer`
panel, `Amount: 0.001 XCH`, `Recipient: your own wallet`, and `This transaction has been checked and
is safe to approve.` — all in the app's own brand language, directly above the real **Sign** button.
Screenshots `C-webview-UNESCAPED.png` vs `D-webview-escaped.png` differ by that single call.

**The CSP the ticket proposed as the backstop would not have stopped it.** The forgery uses no
script — it is markup plus inline `style=` attributes, and dig-installer's own CSP allows
`style-src 'unsafe-inline'`. A script-focused CSP does not constrain HTML injection.

Two supporting facts, not opinions:

- dig-installer — the reference implementation this ticket holds up as the bar — **already contains
  this sink**: `gui/app/src/steps/Installing.jsx:46` renders log lines with
  `dangerouslySetInnerHTML`, guarded by a hand-rolled `escapeHtml()` in `App.jsx:431`. In an install
  log that is cosmetic. In a spend confirmation it is not.
- The Rust-native prototype is fed the *same* payload and has no equivalent switch, because there is
  nothing to switch off: `Painter::text` rasterises glyphs. `<b>` draws as `<`, `b`, `>`.

### Runtime shape

dig-app is a tray-resident daemon spawning short-lived modals. 411 ms and six browser processes per
consent dialog is a materially worse product than 90 ms in one process, and the memory is spent
*while the user is deciding whether to spend money*.

### Costs accepted, stated plainly

- **A second UI idiom in the ecosystem** (egui here, React/Tauri in dig-installer). The user has
  explicitly bought this: *"if you have to duplicate the design system in rust, that is fine, its
  more important we have a proper gui system with good UI."*
- **Gradients, glows and washes are hand-written meshes.** egui has no gradient fill; the
  violet→magenta pill needed a rounded-outline triangle fan with per-vertex colour, and the ambient
  radial wash needed a 20×20 per-vertex grid. ~80 lines, written once, reused everywhere. The first
  attempt looked visibly wrong — polish parity here is deliberate work, not a default.
- **The window must be OPAQUE.** A transparent frameless eframe/winit surface on Windows loses its
  content on any `SetWindowPos` move or restore and never recomposites — the window goes blank.
  So dig-installer's CSS-faked drop-shadow-through-a-transparent-gap is not available; the card is
  drawn edge to edge instead. (Found while building the screenshot harness; recorded because
  "which stack needs bespoke window wrangling to behave like a modal" is invisible in a screenshot.)
- **egui needs a GL context.** On a host without one the prompt cannot draw — which must resolve to
  DENY, the behaviour the ticket already requires of a headless host.

### Bonus the measurement did not ask for

egui gives all three platforms ONE window implementation. That deletes the Linux `zenity`/`kdialog`
subprocess dependency outright — and with it `escape_kdialog_plain`, the `--no-markup` flags, and
the "is a dialog helper even installed" failure mode.

## Theme

Source of truth is `modules/services/hub.dig.net/apps/web/app/globals.css` — `:root` (light, the
default) and `[data-theme="dark"]` (line 77, the opt-in). Ported into ONE Rust module with names
matching hub's CSS variables so a divergence is greppable. Light is the default; the choice is
persisted across prompt spawns and restarts.

## Phase 2 — port

Insertion point is already clean: `confirm/mod.rs` defines `ForegroundWindow::show(&ConfirmContent)
-> WindowIntent` and `ForegroundInput::ask(&InputContent) -> InputOutcome`. The branded GUI is ONE
new implementation of those two traits, shared by all three platforms. `gated_consent`, the
never-blind-sign guard and every fail-closed default are untouched.
