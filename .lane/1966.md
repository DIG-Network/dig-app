# Lane #1966 + #1965 — the recovery-phrase backup file

Two tickets, one code path (`save_phrase_file` / `write_owner_only`):

* **#1966** — a native save-file picker, so the user chooses where the plaintext seed lands
  instead of a fixed, predictable `~/dig-recovery-phrase.txt`.
* **#1965** — an explicit owner-only ACL on whatever path they choose. Windows does NOT honour
  Unix mode bits, so the `#[cfg(not(unix))]` arm's plain `fs::write` left the file on inherited
  profile ACLs (user + Administrators + SYSTEM).

They ship together because #1966 widens the exposure #1965 closes: a user-chosen directory is far
more likely to be synced or shared (Desktop, Documents, OneDrive) than the profile root was.

## What landed

`dig-app-core::secret_file`, a new module holding both halves:

| File | Holds |
|---|---|
| `mod.rs` | `choose_secret_file_path` — the cancel-vs-unavailable decision |
| `owner_only.rs` | `write_owner_only` + the Unix and Windows permission tests |
| `windows_acl.rs` | the protected single-ACE DACL, the ACL inspection, the cross-principal probe |
| `picker/{mod,windows,macos,linux}.rs` | the `SaveFilePicker` seam and the three platform dialogs |

The logic moved OUT of `crates/dig-app/src/bin/dig-app.rs`, where the crate's own manifest says
coverage is not measured. The shell now only addresses the vault and calls the core.

## The two decisions worth remembering

1. **A cancel is not a fallback.** Dismissing the dialog abandons the write. Falling back to the
   old fixed path there would write the seed somewhere the user had just declined.
2. **An unavailable dialog IS a fallback.** A headless host never got to ask, so it keeps the old
   behaviour rather than losing the feature.

## The test that nearly lied

The Windows tests do not read the file — a test running as the owner passes under *any* ACL. Two
layers instead:

* `GetEffectiveRightsFromAclW` for Everyone / Administrators / SYSTEM — the OS evaluating the ACL.
* A **real cross-principal open**: impersonate a restricted token with the owner's SID marked
  deny-only, then `File::open`. That is the kernel's own access check.

The cross-principal test needs **two** controls, and finding out why cost a falsification round. With
only a "the probe can read a world-readable file" control it **passed against a reverted `fs::write`
implementation** — because in a non-elevated session an inherited-ACL file is unreachable by that
token too. The second control (a plain `fs::write` file must be readable) is the one that makes the
comparison mean anything, and it only holds when elevated. Non-elevated sessions now skip loudly
rather than bank the pass; CI runs elevated and exercises it.

## Deliberate, and worth a second opinion

* macOS uses `osascript`'s `choose file name` rather than `NSSavePanel`, even though `objc2-app-kit`
  is linked — a panel needs main-thread dispatch and a modal loop that re-enters the tray's, and none
  of that is verifiable from a Windows dev box. The seam is there if the panel is wanted.
* Linux reintroduces a **soft** `zenity`/`kdialog` dependency that #2038 removed for consent windows.
  Different failure mode: a missing helper degrades to the fixed path, it does not remove the
  capability. Rationale is in `picker/linux.rs`.

## Rebased onto the egui prompt GUI (#69)

Verified rather than assumed after the rebase onto 5.14.1:

* No file under `confirm/**` is touched by this branch; the rebase conflicted only on the version.
* `save_phrase_file` runs on the `ActionWorker` thread, which is where the old native dialogs ran
  too — a modal Win32 common dialog there is the established pattern, not a new one.
* **P0 #2074** (only one prompt per process) breaks the ceremony at the *reveal gate*, before the
  picker is ever reached — and it fails CLOSED: a window that cannot be shown yields
  `WindowIntent::Unavailable` → `ConfirmDecision::Unavailable`, never `Approve`, so
  `back_up_phrase` returns `Refused` and decrypts nothing. End-to-end manual verification of the
  picker is blocked until #2074 lands.
