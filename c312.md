## Screenshot-harness note, from the #306 readout work in PR #311

Recording this here rather than as a new issue, since #312 already owns the surrounding notification
work and this is a finding about the harness that photographs it.

### The blocker round 2 hit was a harness defect, and it is now fixed

`pane_preview` reported *"DIG cannot read its settings file"* and every margin state came out
byte-identical. The cause was not the GPU and not `PrintWindow`: `seed_collateral_preview` built its
session with `store: None`, which **is** the cannot-read-the-settings-file state, so every settings
card drew a banner instead of its body. No preview could ever have photographed any settings card.

Fixed in #311 by `prefs::PreviewStore` — in-memory, reads a default `AgentConfig`, drops writes. It is
deliberately not `#[cfg(test)]`, because the preview is an example compiled against the library and a
test-only fake is invisible to it.

Captures now work: two are committed under `crates/dig-app-core/docs/collateral-funding/`.

### The gap that remains

**The Settings pane is longer than any window this display can open, and the preview cannot open
scrolled to a card.** Scrolling to one would mean driving synthetic input, which a committed
screenshot must never be taken after (dig_ecosystem#2309).

The workaround used in #311 is to pass a low `zoom` (`0.36`) so the whole pane fits one frame. It
works and the text stays legible at 200% DPI, but it means a card cannot be photographed at its real
rendered size, which is exactly what a spacing or contrast review needs.

Two ways out, neither attempted:

1. **A preview argument that draws ONE card**, rather than the whole pane. Cheapest, and it makes each
   card's picture independent of how many cards sit above it — which is what makes the current
   captures fragile: adding a card above shifts every existing shot.
2. **Render to an offscreen surface at arbitrary height** instead of capturing a real window, which
   removes the display-size ceiling entirely.

### Also worth knowing for whoever writes the capture script

`FindWindow(null, "DIG")` **does not find it** even though the window title is exactly `DIG`. Use the
process object's `MainWindowHandle` after a `Refresh()`. The window is `2432x2338` real pixels for a
`960x900` logical request, so any capture path must call `SetProcessDPIAware()` first or it silently
grabs a scaled region.

`PrintWindow` with `PW_RENDERFULLCONTENT` (flag `2`) does return the real client area for this
eframe surface — the round-2 conclusion that it returns a blank client area was, I believe, the
settings-file gating above rather than a compositor limitation.
